# Worked example: shed

`shed` is a fictional Go command-line tool in the `chinmina` organisation. This directory holds the complete set of files that connect it to the shared release pipeline. It is the reference implementation for a CLI tool, built from the release configuration of [`chinmina/kms-import`][kms-import] and [`jamestelfer/imds-broker`][imds-broker].

shed publishes through four channels:

- a GitHub Release with archives for Linux, macOS, and Windows on amd64 and arm64
- an attested `install.sh`, generated by binstaller
- a Homebrew cask in `chinmina/homebrew-tap`
- a Nix recipe in `chinmina/nixpkgs`

It publishes no container image and no npm package. Release tokens come from the `chinmina` release GitHub App (`token-source: app`).

The guide [Adopting the release pipeline](../../guides/adopting-the-release-pipeline.md) explains each file. The guide uses `<OWNER>` where this example uses `chinmina`, and `<REPO>` and `<TOOL>` where this example uses `shed`.

## Files

Paths are relative to this directory and match their location in `chinmina/shed`.

| File | Purpose |
| ---- | ------- |
| [`.github/workflows/release-please.yml`](.github/workflows/release-please.yml) | Calls `release-please.yml` on pushes to `main`. |
| [`.github/workflows/release.yml`](.github/workflows/release.yml) | Calls `goreleaser-release.yml` on `v*` tags. Opts out of Docker login and npm. |
| [`.github/workflows/pr-title.yml`](.github/workflows/pr-title.yml) | Calls `conventional-pr-title.yml`, so squash-merge commit messages follow Conventional Commits. |
| [`release-please-config.json`](release-please-config.json) | release-please configuration, including the three keys the kit requires. |
| [`.release-please-manifest.json`](.release-please-manifest.json) | Version manifest. `0.0.0` means unreleased; the first release is `0.1.0`. |
| [`.goreleaser.yaml`](.goreleaser.yaml) | Build, archive, release, Homebrew cask, and Nix recipe configuration. |
| [`mise.toml`](mise.toml) | Tool versions, including the `binstaller` alias. |
| [`.config/binstaller.yml`](.config/binstaller.yml) | binstaller spec generated from `.goreleaser.yaml`. |

## Repository settings

These settings live in GitHub, not in files.

| Setting | Value |
| ------- | ----- |
| `automation` environment | Deployment policy: branch `main`. Secrets: `RELEASE_PLEASE_CLIENT_ID`, `RELEASE_PLEASE_APP_PRIVATE_KEY`. |
| `release` environment | Deployment policy: tag `v*`. Secrets: `RELEASE_PLEASE_CLIENT_ID`, `RELEASE_PLEASE_APP_PRIVATE_KEY`. |
| Release GitHub App | Installed on `shed`, `homebrew-tap`, and `nixpkgs`, with `contents: write` and `pull_requests: write`. |
| Rulesets | The release App is an `always` bypass actor on any `v*` tag ruleset in `shed`, and on the default-branch rulesets of `homebrew-tap` and `nixpkgs`. |

## Notable choices

### Caller workflows

- Both callers pass the two App secrets by name. GitHub resolves them in the environment of the reusable job that uses them, so environment-only secrets arrive. `secrets: inherit` would also work for a `chinmina` repository, but passes nothing to a reusable workflow under a different owner.
- The release-please caller grants `id-token: write` although the `app` token source does not use it. The reusable job declares it, and a caller that grants less fails at startup.

### release-please

- `release-type: simple` records the version in the manifest only. goreleaser stamps it into the binary through `ldflags`, so no source file needs rewriting.
- `draft`, `force-tag-creation`, and `include-component-in-tag: false` are set at the top level. Package entries inherit them, and the kit's validator accepts either placement.
- `pull-request-header` and `pull-request-footer` are the standard text shared by every repository using the kit.

### goreleaser

- Release notes come from release-please. `mode: keep-existing` keeps them, so the config has no `changelog` block.
- The cask clears the macOS quarantine attribute with `postflight_steps` inside `custom_block`. Homebrew deprecated the `postflight` stanza that `hooks.post.install` produces, and the `url.verified` parameter. The cask uses neither.
- The cask has no `binaries` list. goreleaser defaults to the build's binary, and `binst` 0.12.0 fails to load a config that sets `homebrew_casks[].binaries`.
- The Nix recipe has no `main_program` or `formatter`, which `binst` 0.12.0 also rejects.
- `skip_upload: auto` on both the cask and the recipe stops prerelease tags from publishing to either package repository.

### Version stamping

`ldflags` sets `github.com/chinmina/shed/internal/buildinfo.Version`. The package defaults the value to `dev`, so local and `go install` builds report `dev`:

```go
// internal/buildinfo/buildinfo.go
package buildinfo

// Version is overridden at link time by goreleaser.
var Version = "dev"
```

## Install commands

These are the install commands shed's own `README.md` documents, one per channel:

```sh
mise use -g github:chinmina/shed
curl -fsSL https://github.com/chinmina/shed/releases/latest/download/install.sh | sh
brew install chinmina/tap/shed
nix profile install github:chinmina/nixpkgs#shed
go install github.com/chinmina/shed/cmd/shed@latest
```

Every downloaded artifact is verified with:

```sh
gh attestation verify shed_linux_amd64.tar.gz --repo chinmina/shed \
  --signer-workflow chinmina/.github/.github/workflows/goreleaser-release.yml
```

`--signer-workflow` is required. The shared workflow in `chinmina/.github` signs every attestation, so `--repo` alone looks for a signer in `chinmina/shed` and fails.

## octo-sts token source

An owner with [octo-sts][octo-sts] instead of a release App changes only the two callers. Set `token-source: octo-sts`, and remove the `secrets:` block, because nothing is stored. The environments then hold no secrets.

```yaml
# .github/workflows/release-please.yml (octo-sts token source)
jobs:
  release-please:
    permissions:
      contents: read # read the release-please config
      id-token: write # octo-sts token exchange
    uses: chinmina/.github/.github/workflows/release-please.yml@verified-actions
    with:
      token-source: octo-sts
```

```yaml
# .github/workflows/release.yml (octo-sts token source)
jobs:
  release:
    permissions:
      contents: write
      id-token: write # octo-sts token exchange and keyless attestation
      attestations: write
    uses: chinmina/.github/.github/workflows/goreleaser-release.yml@verified-actions
    with:
      token-source: octo-sts
      disable-docker-login: true
      disable-npm: true
```

The owner must define trust policies for the identities the workflows request: `release-please-shed`, `release-shed`, and `release-tap`. Policies are owner configuration, documented by the owner.
